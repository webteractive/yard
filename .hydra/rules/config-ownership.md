# Config ownership

Herd overwriting user config is one of the pain points Yard exists to fix. Keep it fixed.

- **Three kinds of file.**
  - Generated files start with `# Generated by Yard — edit <overrides path> instead`
    (`<!-- … -->` in HTML) and have their sha256 recorded in `state/hashes.json`.
    The `conf.d` inis (`10-brew-*.ini`, `50-<ext>.ini`) are generated and name
    `yard.toml` as the file to edit; `overrides_for` maps them. So are a service's
    `services/<instance>/my.cnf` or `redis.conf` and `nginx/services/minio.conf`
    (`minio.<tld>`, left out when a site has the name), which name the instance's
    `overrides.conf`; `nginx/services` is a managed directory, so a block nothing renders any more
    is removed. Reconcile renders them with the instance's pinned ports from the registry, never
    the engines' usual ones, and restarts the instance when its config file changed. It creates
    `services/<i>/data` for Redis only (redis-server exits at config load without its `dir`); the
    databases' init needs theirs absent or empty, and MinIO makes its own.
  - Yard never re-initializes a database's data: `yard doctor` fails `service-data:<i>` for a MySQL or
    PostgreSQL instance whose `data/` is missing or empty and names `yard service remove <i> && yard
    service add …`; it reads Redis's and MinIO's directories not at all.
  - User-owned files (`nginx/overrides/<site>.conf`, `php/<v>/conf.d/99-overrides.ini`,
    `services/<instance>/overrides.conf`)
    are created once with `ensure_user_file` (empty, or a comment saying whose they are) and never
    written again. A MySQL instance's `overrides.conf` starts with that comment and `[mysqld]`, since
    an `!include`d file needs its own group (`services::render::user_overrides`); a PostgreSQL
    instance has none, since its user file is `data/postgresql.conf`, which `initdb` writes. The one
    exception to "never written" is
    `99-overrides.ini` through `yard php config set|unset` (`rpc/php.rs`
    `config_edit`, via `yard_core::ini`, which keeps every other line as written,
    and `generated::write_preserving`, which writes through a symlink and keeps the mode).
  - `services.add` writes the `services.toml` entry and the pinned `ports.toml` entries, through
    `TomlFile` (`services::Add`), and `services.remove` deletes them. A failed or cancelled add
    deletes only what it created in `services/<i>/`: a file or directory that was there before (the
    user's `overrides.conf`, or data left by `remove --keep-data`) stays, and so does `data/` when the
    add reused it. `remove` deletes the whole directory, or all but `data/` with `keep_data`, and only
    once the unit is gone.
  - `services.stop` sets `stopped = true` on an instance's `services.toml` entry and `services.start`
    removes the key (never `stopped = false`), both through `TomlFile` (`services::set_stopped`)
    and then reconcile. The edit itself checks the entry is still there (`SERVICE_NOT_FOUND`
    otherwise): setting a key under a missing table would write a stub entry that `services.toml`
    cannot parse. Nothing else, `services.restart` included, ever clears `stopped`.
  - Sleep (M4e) is opt-in user config: `service_sleep_after` in `yard.toml` and `sleep_after` per
    instance in `services.toml` (`"15m"`, `"off"`, at least 60 s; the instance key wins).
    `services.sleep.set` writes or removes the instance key through `TomlFile`
    (`services::set_sleep_after`); nothing else writes either key. Whether an instance sleeps is
    runtime state in yardd's `Sleeper`, never written to a TOML: sleeping is not `stopped`.
  - `run/sleeping` is generated (M4e): the linked sites that need a sleeping or draining
    instance, or one whose wake was refused over a held port, one per line, written atomically (`sleep::write_sleeping`) in every reconcile when
    it changed, before that reconcile stops or starts a unit, so a site is listed from the moment
    its instance starts to drain, through its stop (the reconcile is its only writer, under its
    lock, and `Reconciler::wake_from_last_good` under the same lock), and emptied at yardd start
    before the first reconcile. The shims read it; nobody edits it.
  - The reconcile forgets the sleep of an instance that is stopped, removed, or no longer set to
    sleep, so editing a TOML always undoes a sleep; and it renders the nginx wake hook only for a
    site that needs an instance which may sleep.
  - User TOMLs (`yard.toml`, `sites.toml`, `ports.toml`, `services.toml`) are edited only through
    `config::edit::TomlFile` (`toml_edit`), so comments and key order survive. Every
    read-modify-write in the daemon is one `TomlFile::edit(path, |file| …)`, which holds
    a process-wide lock from load to save, so an RPC and a job never lose each other's
    change; never `load` then `save` by hand, and never put old bytes back to undo an
    edit (remove the entry instead).
- **Write rule** (`generated::plan`): compare against the stored hash, not just the
  render. A hand-edited file whose render did not change is left alone and reported by
  `yard doctor`, which names the override from `render::overrides_for` (a test keeps it
  in step with each file's header). A hand-edited file whose render changed is copied to
  `<file>.yard-backup` before it is written. A file with no stored hash is never deleted.
- Every config change that touches `nginx/` runs `nginx -t` from yardd, as the user
  (`nginx::NginxCommand::test`). On failure, roll back the whole write set and return
  `NGINX_CONFIG_INVALID` with nginx's output. An nginx that cannot run at all is a
  warning on reconcile and a refusal on `yard restart nginx`.
- User overrides are applied too: the watcher sees `nginx/overrides/`, and the `overrides.conf`
  of every instance nginx includes it for (MinIO's, in `minio.<tld>`'s block; `watch.rs`
  `nginx_include_dirs`, re-read when `services.toml` changes, with one `nginx -t` after a watch is
  added), and calls `Reconciler::apply_overrides`, which runs `nginx -t` and reloads only if it
  passes. MySQL's and Redis's `overrides.conf` are not watched: a restart of the instance applies
  them.
  `yard restart nginx` tests first and refuses a broken config, so a typo in an
  override never takes sites down.
- A TOML parse error never takes sites down. Keep the last good snapshot and report
  `CONFIG_INVALID` with file, line and column. Values that would break a render are
  parse errors too (`tld` against `valid_tld`, two units on one port), located at
  their span. Every failed reconcile is kept in `State.last_error`, which `status`
  and `doctor` report until a reconcile succeeds.
- **Quote every path** in rendered output. The data root is `~/.yard` by default, but
  `YARD_ROOT` and project directories can hold spaces, which break unquoted nginx, fpm and
  ini values (render tests keep a root with a space for that reason).
  The one exception is `!include <path>` in a service's `my.cnf`: mysqld treats a quote there as
  part of the path, so it is written bare, and the rest of the line is the path.
- **A project's `.yard` is the project's file**, committed with it (project-file spec).
  Yard reads it at most 64 KiB and only as a regular file, and writes it only in
  `yard init` (`rpc/project.rs`): `project::render` for a new one, `project::rewrite`
  (`toml_edit`, keeping every other key and comment) with `--force`, never through a
  symlink. Reconcile, doctor and the shims only read it. Settings it owns
  (`php`, `docroot`, `secure`) are refused by `isolate`, `secure` and `docroot` with
  `SITE_HAS_PROJECT_FILE`, whose hint is the edit to make in the file. `[services]` is the
  user's to uncomment: `project::render` writes it as comments only, and `rewrite` keeps it.
  `yard init` writes it only with `--local`.
- **A managed `.yard` (`<root>/sites/<name>/.yard`, managed-file spec) is the user's file
  in Yard's data root.** Plain `yard init` writes it (`project::render_managed`, with
  `project = "<path>"` exactly as `sites.toml` spells it), `--force` rewrites it, and
  `--local` moves it into the project (`project::to_committed`) and deletes it.
  `isolate`, `unisolate`, `secure`, `unsecure` and `docroot` edit it through
  `managed::edit_managed`, which takes `TomlFile`'s lock, keeps every other key and
  comment, refuses a file that does not parse before or after the edit, and never writes
  through a symlink (`INVALID_ARGUMENT`, hint `edit <link target>`). `init --replace` over
  another project's file keeps it as `sites/<name>/.yard-backup` first. `yard unlink` never
  deletes it. A committed `.yard` always wins, and Yard never edits or deletes the managed
  file it hides.
- toml_edit keeps the comment lines above a key in that key's decor. `TomlFile::set`
  replaces an existing key's value in place, so they survive (`insert` would drop them),
  and `TomlFile::remove` moves them onto the value that follows in the same table, else
  above the next table header the file prints (toml_edit prints tables by their parsed
  position, not key order), else to the start of the file's trailing comments (where a
  managed `.yard`'s commented `[services]` block is). A table the removal empties goes with
  its header, and the comments above that header move the same way. Removing never deletes
  a comment.
- **Node (M4c spec §10).** `<root>/node/` is fnm's (`FNM_DIR`): Yard writes nothing inside it
  except through `fnm install`/`uninstall`, never deletes the directory, and removes only a
  `node-versions/v<x>` with no `bin/node` (a failed download) before retrying. `node/lts.toml`
  is generated (`write_lts`, header and all) from each `fnm ls-remote`. `default_node` in
  `yard.toml`, a site's `node` in `sites.toml` and the `node` key of a `.yard` are the user's,
  edited only by `yard node default` and `use`/`unuse` through `TomlFile` or
  `managed::edit_managed`, and `use`/`unuse` are refused for a committed `.yard`. A project's
  `.nvmrc` and `.node-version` are read only (at most 64 KiB, regular files).
- Yard never writes project `.env` files (spec non-goal).
