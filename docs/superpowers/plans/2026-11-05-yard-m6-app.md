# M6 Yard.app Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Yard.app, a SwiftUI menu bar app and main window that is a pure JSON-RPC client of
yardd, with live state from events, job progress, errors with fix actions, and onboarding.

**Architecture:** Three small Rust changes first (wire fixtures for the app, a `reconciled` event,
`php.list { available }`, protocol 2.11). Then a local Swift package in `app/`: `YardKit` (wire
models checked against the Rust fixtures, NDJSON framing over a POSIX unix socket, a reconnecting
client with separate call, event and log connections, the CLI runner) and `YardModel`
(`@Observable` models, jobs, actions, hint parsing, flows, onboarding facts), both tested with
`swift test`. Last, a Tuist app target with the SwiftUI views, which holds no logic worth a test.

**Tech Stack:** Rust workspace (yard-proto, yard-daemon, yard-cli), serde_json; Swift 6.3.3
(language mode 6, `swift-tools-version: 6.0`), SwiftUI and Observation on macOS 14+, Swift
Testing, Foundation `Process`, POSIX sockets with `DispatchSourceRead`; Tuist 4.200.5 (through
mise) and Xcode for the app bundle.

**Spec:** `docs/superpowers/specs/2026-11-05-yard-m6-app-design.md` (draft, not approved). Main
spec: `docs/superpowers/specs/2026-10-19-yard-design.md` (§3.1, §6, §9, §10, §12).

## Assumptions from the open questions

The design's §18 questions are not answered yet. This plan assumes the recommended answer to each;
a task that depends on one says so in its first line.

- **Q1** the helper stays `sudo yard helper install`, handed to Terminal; no `SMAppService` in M6.
- **Q2** hand-written Swift models checked against Rust-written fixtures; no JSON Schema.
- **Q3** the app carries no binaries; it uses the `yard` beside the LaunchAgent's yardd.
- **Q4** protocol 2.11 adds `reconciled` and `php.list { available }` in M6.
- **Q5** a menu bar app (`LSUIElement`), with a Dock icon only while the main window is open.
- **Q6** Tuist plus a local Swift package, as zetty does.

## Global Constraints

- macOS 14+, arm64 only; Swift language mode 6 with strict concurrency; `swift-tools-version: 6.0`;
  no third-party Swift packages; tests use Swift Testing (`import Testing`).
- No Swift feature newer than the CI runner's Swift: no `@concurrent`, no module-wide default
  `MainActor` isolation. Task 4 records the runner's Swift version in the CI job's log.
- `YardKit` imports only Foundation, Darwin and Dispatch; `YardModel` adds Observation; only the app
  target imports SwiftUI or AppKit.
- The app never writes a file in Yard's data root or a project, never runs `brew`, `launchctl`,
  `security`, `sudo` or a shell, and never passes a hint's text to anything that runs it. The `yard`
  CLI is run with an argument array and `--json`.
- Bundle id `dev.more.yard.app`; `LSUIElement` true; no App Sandbox.
- Protocol `"2.11"`; `hello.client` is `Yard.app <CFBundleShortVersionString> (<YardBuildCommit>)`.
- Call timeout 60 s. Reconnect after 0.25 s, 0.5 s, 1 s, 2 s, then every 5 s.
- Socket paths at most 104 bytes; test sockets under `/tmp/yard-app-test-<random>`.
- Wire models: explicit snake_case `CodingKeys`, no key coding strategies; every wire enum has an
  unknown case that keeps the raw value; `ErrorCode` is a `String`-backed struct.
- Client-made errors use the CLI's words: `yardd is not running` (`DAEMON_NOT_RUNNING`, hint
  `yard start`); `lost the connection to yardd: <e>` and `yardd closed the connection` (`INTERNAL`,
  hint `yard doctor checks why`); `yardd did not answer <method> within 60 s` (`INTERNAL`, hint
  `yard doctor checks what is stuck`); `yardd answered <method> in an unexpected shape: <e>`
  (`PROTOCOL_MISMATCH`, hint `upgrade yard and yardd together`); `yardd speaks protocol <p> and has
  no <method>` (`METHOD_NOT_FOUND`, hint `yard stop && yard start`).
- Tests never touch `~/.yard`, the real LaunchAgent, Herd, `/etc/resolver` or a real port, and
  never run a real `yard start`, `stop`, `trust` or `helper`.
- Rust: no new crates; `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`
  and `cargo test --workspace` pass after each Rust task. Never plain `cargo clean`.
- Disk is tight: at the end of a session that built, remove `app/.build` and `app/Derived`, and
  `cargo clean --profile dev` if a Rust task built; never `target/release` (the LaunchAgent runs
  it). Report what was removed.
- Work on main. Commit messages: a lowercase prose subject, prose paragraphs, no type prefix, no
  trailers. Ask the maintainer before each commit.

## Review Focus

The five failure modes most likely to bite a person using the app, each pinned by a test in the
task named:

1. **yardd restarts while a job runs, and the next job reuses its id** (`php-install-1` again):
   the old job shows lost, the new one is a separate record (Task 12,
   `a_reused_id_after_reconnect_is_a_new_job`).
2. **A job fails before its call answers** (a refused install finishes in microseconds): one
   record, and `runJob` still returns the failure (Task 12, `finished_before_the_answer_returns`).
3. **yardd was not restarted after a build** (it speaks 2.10, the app 2.11): `subscribe` leaves out
   `state`, so the subscription does not fail and events still arrive (Task 9,
   `stale_daemon_subscribes_without_state`).
4. **A path or hint with a space, a quote or shell syntax**: a Terminal hand-off quotes every
   argument, and a hint like `rm -rf ~/x` or `yard service start "a b"` is only offered to copy
   (Task 13, `unknown_and_malformed_hints_only_copy`; Task 14, `command_file_quotes_every_argument`).
5. **A large answer split across reads, and two events in one read** (a 300 KB site list):
   framing delivers each line whole and in order (Task 7, `lines_survive_any_chunking`).
